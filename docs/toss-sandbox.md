# 토스 SDK v2 주문서형 샌드박스

`pueblo/public/toss-sandbox.json`의 clientKey에 위젯용 `test_gck_` 클라이언트 키를 설정합니다. 이 파일은 공개 설정입니다. 시크릿 키를 넣으면 안 됩니다. 배포 시 이 정적 파일을 교체해도 되며 Docker 빌드 ARG는 필요하지 않습니다.

장바구니에서 상품을 선택하고 동의 후 결제하기 → /checkout에서 결제수단·약관 위젯 → 테스트 결제 → 인증 결과 화면 순서입니다. 모바일도 지원하는 successUrl/failUrl 리다이렉트를 사용합니다. SDK 및 위젯 UI 준비 전에는 결제 버튼이 비활성화됩니다.

승인 결과는 서버 응답으로 판단합니다. 프론트 금액 비교는 UX 검증이며 최종 주문 소유자·금액·재고 검증은 백엔드가 수행해야 합니다.

참고: https://docs.tosspayments.com/sdk/v2/js/payment-widget

## 주문·승인 백엔드 연결

개발 모드에서는 주문 API `http://localhost:8083/api/v1`, 결제 API `http://localhost:8084/api/v1`를 사용합니다. 배포 빌드는 같은 출처 `/api/v1`을 사용하므로 Ingress/Gateway에서 주문·결제 경로를 각 서비스로 라우팅해야 합니다. 개발 서버 출처(예: localhost:5173)에 대한 CORS 및 Authorization, Idempotency-Key 헤더 허용이 필요합니다.

로그인 토큰은 기존 로그인 구현과 동일하게 localStorage의 `token`에서 읽습니다. 주문 소유 회원의 accessToken이어야 합니다. 토큰이나 paymentKey는 로그에 출력하지 않습니다.

장바구니 → /checkout/new에서 배송지와 구매 약관을 입력 → 견적 → 멱등키로 주문 생성 → 주문 상세에서 PENDING_PAYMENT 확인 → 서버 totalAmount로 위젯 결제 순서입니다. PREPARING이면 잠시 후 주문 확인 버튼으로 재조회합니다. 결제창을 열기 직전에도 서버 상태·금액을 재확인합니다.

현재 샘플 상품에는 실제 productId·skuId가 없습니다. 상품 API 연결 전에는 기존 본인 주문 UUID를 입력하는 경로를 이용합니다. 실제 상품을 연결할 때 CartItem의 productId, skuId를 채워야 합니다. 임의 UUID로 상품이나 주문을 대체하지 않습니다.

주문 생성의 본문·멱등키는 세션에 저장해 재시도 시 유지합니다. 네트워크 오류 후 임의로 새 주문을 생성하지 마세요. 기존 요청과 다른 배송지·상품으로 다시 제출하면 먼저 이전 주문을 확인하도록 차단합니다.

인증 결과 화면에서 '결제 승인 요청'을 누르면 서버 주문 금액을 재검증하고 승인 POST를 전송합니다. 요청을 전송한 기록이 있으면 이후에는 GET 상태 조회만 수행합니다. 응답이 불확실하거나 처리 중이면 '결제 상태 다시 확인'으로 재조회합니다. data.status가 SUCCEEDED인 경우에만 '결제 승인 성공'을 표시합니다. 주문 완료 및 재고 확정은 백엔드 미구현이므로 성공으로 표시하거나 장바구니를 비우지 않습니다.

실제 백엔드 데이터·로그인 계정으로 E2E 승인은 별도 검증이 필요합니다.
